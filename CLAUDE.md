# GastroMetrics

Sistema de gestión gastronómica (fichas técnicas, costeo, inventario, menús, órdenes de compra) para restaurantes en Centroamérica. Next.js 14 + React 18 + TypeScript + Tailwind + shadcn/ui. Backend real (Supabase + Stripe + Resend) para auth, planes, datos de negocio y correo transaccional, verificado de punta a punta contra el proyecto real (ver `docs/52`-`docs/57`) — sigue en `localStorage` puro solo el sistema de Equipo (aunque la invitación ya manda correo real, ver `docs/55`) y la importación de ventas del POS (Fase 4 sin implementar).

## Primer comando a correr

```bash
npm install && npm run build
```

(El lockfile presente es `package-lock.json`, no `pnpm-lock.yaml` — `pnpm` no está instalado en este entorno. `npm run build` ejecuta lo mismo que pediría `pnpm build`.) Verificado exitoso por primera vez en `docs/29` (`exit code 0`, 33 rutas) — antes de eso el proyecto nunca había pasado un build real. Si vuelve a fallar, compara contra ese documento antes de asumir que es un problema nuevo.

Si el build falla, revisa primero `package.json`: `react`/`react-dom` deben estar en `^18` (Next 14.2.25 no soporta React 19 oficialmente — esto ya causó un error de build real en una sesión anterior, ver `docs/10-build-fix-idiomas-monedas-pdf.md`, sección 1). También revisa cualquier uso nuevo de `useSearchParams()` sin envolver en `<Suspense>` — rompió el build 3 veces antes de corregirse, ver `docs/29`, sección 1.

**Nunca corras `npm run build` con `next dev` activo en la misma carpeta** — corrompe los artefactos que el servidor de dev tiene cargados (404/500 fantasma en el navegador hasta reiniciar). Detén el dev server primero, corre el build, y si vas a seguir probando en vivo después, borra `.next` y reinicia el dev server limpio (ver `docs/30`).

`npm test` corre la suite de pruebas automatizadas (Vitest, ver `docs/29` sección 3) — 20 pruebas sobre aislamiento de storage por negocio, la cascada de recálculo de precios, el redondeo de precio de venta, y el costo promedio ponderado.

## Decisiones de negocio ya confirmadas (no volver a preguntar)

- Redondeo de precio: un solo redondeo, en precio de venta unitario, hacia el 5 más alto.
- Los seis rubros de costeo son % sobre costo de producción, no sobre precio de venta.
- ISV/impuesto: 0 por defecto, opcional, sin lógica de país específica.
- Escalado de recetas/menús: cantidades de ingredientes siempre redondean hacia arriba.
- Papelera de recetas: 30 días antes de purgar automáticamente.
- Multiusuario: cada quien crea su propia cuenta; el dueño del negocio comparte la suscripción vía link de invitación (pendiente de backend real para implementarse).
- Monedas soportadas: todas las centroamericanas + China + USD + Euro (`lib/currency.ts`).
- Idiomas soportados: español, inglés, danés, francés, portugués, chino — solo texto visible al usuario, no traducción completa de código/datos (`lib/i18n/`).
- Planes de suscripción con bloqueo real de funciones (5 tiers: Foodie/Home Cook/Chef de Partie/Sous Chef/Chef Ejecutivo, ver `docs/33`): catálogo en `lib/plans.ts`, control de acceso en `lib/plan-access.ts`. Un plan por cuenta, ahora real vía Supabase (`account_plans`) y Stripe — ver `docs/52`. `localStorage` solo guarda un caché local de lectura instantánea, ya no es la fuente de verdad. No modificar los límites/features de cada plan sin confirmar con el dueño del proyecto — es tabla de precios de negocio, no un detalle técnico. Hasta 10 correos en `TESTER_ALLOWLIST_EMAILS` (variable de entorno, nunca en el código) reciben plan Chef Ejecutivo gratis al iniciar sesión, sin pasar por Stripe — ver `app/api/plan/dev-account/route.ts`.

Ver `docs/01-especificacion-funcional.md` y `docs/04-lineamientos-diseno-negocio.md` para el detalle completo de estas decisiones y su razonamiento.

El deploy a Vercel ya es automático en cada `git push origin main` — la conexión GitHub↔Vercel se depuró y quedó funcionando (ver `docs/53` para la causa real: la cuenta de Vercel estaba autenticada con un GitHub distinto al dueño del repo).

**Correos transaccionales con diseño de marca real** (paquete de 6 plantillas entregado externamente, `lib/email-templates/*.html`, ver `docs/53`): confirmación de registro, respuesta a feedback, recuperación de contraseña, cancelación de suscripción, y cambio de plan ya mandan con la plantilla de marca (naranja `#F05324`, logo, un solo CTA) en vez del texto plano/genérico de antes. La pieza clave: registro y recuperación de contraseña **ya no dependen de que Supabase mande su propio correo** — `app/api/auth/signup/route.ts` y `app/api/auth/forgot-password/route.ts` usan `admin.generateLink()` (crea la cuenta / genera el link real SIN mandar ningún correo de Supabase) y el envío lo hace esta app con Resend. Esto significa que el pendiente de "configurar SMTP en Supabase" (que requería que el dueño del proyecto pegara la API key de Resend a mano en el dashboard) **ya no bloquea nada de esto** — solo sigue pendiente para la plantilla nativa de "cambio de correo" de Supabase, que no vino en este paquete de diseño y sigue siendo el flujo genérico. La plantilla de invitación a equipo (`04-invitacion-equipo.html`) **ya está conectada** desde `docs/55`: invitar desde `/equipo` manda un correo real y crea una cuenta real de Supabase Auth (`app/api/team/invite/route.ts`, mismo patrón `admin.generateLink()`). Lo único que falta para Fase 4 completa es la tabla de membresías que conecte esa cuenta nueva con el negocio/alcance invitado — `business_members`/`business_invites` **ya existen en el esquema real de Supabase** (creadas desde la Fase 1, esquema mínimo `business_id`/`user_id`/`role`) pero vacías y sin ningún código que las use todavía.

**Pendiente encontrado, esperando confirmación del dueño** (ver `docs/55`): el webhook de Stripe sigue apuntando a `https://gastrometrics-kappa.vercel.app/api/webhooks/stripe` (el dominio de Vercel anterior a `gastrometrics.org`) — ese subdominio todavía responde, así que no es una falla activa hoy, pero es frágil. Cambiarlo requiere tocar la cuenta de Stripe, no solo código, así que no se hizo sin confirmar primero.

Recuperación de contraseña real (`/forgot-password` → `/reset-password`) y un panel en `/admin` ("Cuentas y planes") para buscar cualquier cuenta por correo y cambiarle el plan manualmente — el mecanismo para migrar testers a un plan pagado cuando el dueño decida, sin mover ningún dato (los negocios ya están ligados a la cuenta real, cambiar el plan no los toca).
